# Review of soiree, September 2026

A first pass that was cut short, written down so the work is not lost. What
it established is below and was checked by hand against the code at `ac033e0`
(v1.2.1). The full pass is designed but has not run: its plan is the second
half of this document, and the script that executes it is
[`.claude/workflows/soiree-improvement-review.js`](../../.claude/workflows/soiree-improvement-review.js).

## How this came about

The question was "look at the soiree app and tell me how to improve". The
approach chosen was to review the code from thirteen angles at once, hand
every finding to independent skeptics, and rank only what survived. The first
run started in a container that allows two reviewers at a time, and the several
hundred agent runs the design needs would have taken the better part of a day
there, so it was stopped after the preliminary checks. Nothing below is a
guess; each line was verified against the file it names.

### The changelog counts each change twice

`CHANGELOG.md` for 1.2.1 lists the run-up crowding fix under both `9e65ffc`,
the branch commit, and `8ffd3a0`, the merge commit; the same happens to the
service-worker fix, the push fixes and, in 1.1.1, the compression change.
GitHub writes a pull request's title into the merge commit's body, so a merge
commit of a pull request titled `fix(web): ...` carries a conventional commit
of its own, and release-please parses the whole message. Every change on a
conventionally titled branch is therefore read twice: once from the branch
commit and once from the merge. Squash merging, which leaves one commit per
pull request on `main`, stops it, and `CONTRIBUTING.md` already tells authors
that the squashed title is what release-please reads.

## Plan for the full review

### Shape

Four phases, all read-only against the repository:

1. **Find.** Thirteen reviewers, one per dimension below, each reading the
   real code and returning up to twelve findings with file, line and quoted
   evidence. Each is told the house rules and pointed at the sections of
   `architecture.md` that record deliberate decisions, so a finding that
   contradicts one has to say so and argue the case.
2. **Verify.** Every finding goes to two independent skeptics. One is asked
   whether it is *true* of the code right now and told to refute it if the
   problem is handled elsewhere or the evidence is misread. The other assumes
   it is true and asks whether it is *worth* the maintainer's time for a tool a
   dozen people use for one evening, refuting anything that restates a known
   roadmap item without a plan, contradicts a documented decision, or is out
   of scope. A finding survives only if both let it through.
3. **Critique.** One agent sees the dimensions, their coverage notes and every
   title, and names up to four things nobody looked at. Those get a reviewer
   and the same verification.
4. **Synthesize.** An editor merges duplicates and writes the report: where it
   stands, fix now, quick wins, structural, product, docs drift, and what was
   considered and set aside.

Verification happens per dimension as soon as that reviewer finishes, not
after all thirteen, so the slowest reviewer does not hold up the rest.

### Running it

From Claude Code at the repository root, ask for the
`soiree-improvement-review` workflow, or hand it the script path directly.
Arguments, all optional:

| Argument | Meaning |
|---|---|
| `repo` | absolute path of the checkout; default is the working directory |
| `outDir` | where scratch files and the final `synthesis.md` land; default `/tmp/soiree-review` |
| `dimensions` | a subset of the keys above, to split the run across machines or workflows |
| `lean` | `true` uses one combined skeptic per finding instead of two |
| `skipCritique` | `true` leaves out the second round |

Size, honestly: thirteen reviewers, up to twelve findings each, two skeptics
per finding, a critic, up to four more reviewers and their skeptics, and an
editor, which is a few hundred agent runs. The Workflow tool caps concurrency
at `min(16, CPUs - 2)`, so on a machine with two spare cores it takes a day and
on one with eighteen it takes an afternoon. Splitting the dimensions across
several workflows in parallel multiplies the cap.

Reviewers that need the binary start it themselves on fixed ports so they do
not collide: `performance` on 18080, `product-gaps` on 18081, `measurements` on
18082, `docs-drift` on 18083, each with metrics 1000 higher. Only
`measurements` runs `npm ci`, the browser suite, or the database-backed Go
tests. Nothing writes inside the checkout.
